# 코딩 스타일

TypeScript 코드를 쓰기 전에 읽는다. 형식, 이름, 주석, 도구 규칙이다. 파일 안의 모양을 다룬다. 설정 파일은 `biome.json`과 `eslint.config.mjs`이고 검사 스크립트는 `scripts/checks/`에 있다.

## 코딩 스타일

- 변수·함수는 `camelCase`, 타입·인터페이스는 `PascalCase`, 상수는 `UPPER_SNAKE_CASE`.
- **`if`·`else`·`for`·`while`·`do` 등 모든 제어문은 반드시 중괄호를 쓰고, 여는 중괄호 뒤에서 반드시 줄을 바꾼다.** 본문이 한 문장이어도 마찬가지다. `if (조건) return;`처럼 한 줄에 쓰지 않는다.

  ```ts
  if (조건식) {
    return;
  }
  ```
- else·else if는 사용하지 않는다. 가드 절(Guard Clause), 메서드 추출(Extract Method), Object Lookup 중 하나로 대체한다. 삼항 연산자는 허용한다.
  - **하나의 조건 안에 `&&`·`||`로 여러 검사를 묶는 것도 피한다.** 검사마다 독립된 가드 절로 나눈다. 조건이 왜 거부됐는지 한눈에 드러나고, 검사 하나를 추가·제거할 때 다른 검사를 건드릴 필요가 없다.
- **함수 본문은 5줄 이하로 유지한다.** 6줄 이상이 되면 Extract Method로 쪼갠다.
  「Five Lines of Code」(Ferenc Bereczki) 기준의 줄 수 계산법을 그대로 쓴다. 물리적 소스 줄이 아니라 **문장(statement) 개수**를 센다.
  - 한 문장이 여러 줄에 걸쳐도 1줄로 센다. 닫는 중괄호만 있는 줄과 빈 줄은 세지 않는다.
  - `if`·`for`·`while` 같은 제어문의 머리(조건)는 그 자체로 1줄이고, 블록 안의 문장은 각각 따로 센다.
  - `try`도 `if`와 같은 방식으로 센다. `try {`와 `catch (...) {`가 각각 1줄이다. **`try` 블록 안에는 호출 하나만 둔다.** 여러 작업이 필요하면 하나의 함수로 추출한 뒤 그 함수 하나만 호출한다.
  - ESLint에 이를 자동 검사하는 규칙이 없으므로 사람이 직접 센다.
- 매직 넘버는 이름 있는 상수로 추출한다.
- 중복 코드는 세 번째 등장 시 반드시 추출한다(Rule of Three).

## 주석

- **주석은 가능하면 쓰지 않는다.** 좋은 이름은 주석을 필요로 하지 않는다. 주석을 달고 싶으면 먼저 이름을 고치거나 함수를 추출해 코드가 스스로 말하게 한다.
- 의도가 명확해야 할 때(왜 그렇게 하는지)와 설명이 필요할 때(수식, 외부 제약, 코드만으로 드러나지 않는 결정)에만 주석을 단다. 무엇을 하는지 되풀이하는 주석, 코드와 어긋난 주석, 옛 설명은 지운다. 주석은 올바르게 쓰거나 지운다. 둘 중 하나다.
- 문서 주석(`/** ... */`)을 쓸 때는 세 줄로 쓴다. 한 줄 형태는 금지다(아래 「한 줄 JSDoc」).
- 설계 결정의 배경은 주석이 아니라 문서에 남긴다.

## 이름 — 줄임말 금지

- 폴더, 파일, 변수, 함수, 매개변수, 속성, 타입, 테스트 이름 모두 낱말을 풀어 쓴다. 금지 예: `dt`(`deltaSeconds`), `ctx`(`context`), `i`·`idx`(`index`), `tmp`(`temporary`), `cb`(`callback`), `vx`(`velocityX`), `tx`(`targetX`), `num`(`count`나 `number`가 뜻하는 이름), `info`(`information`).
- 한 글자 이름은 좌표 `x`, `y`, `z`만 허용한다. 반복 변수와 콜백 인자도 뜻 있는 이름(`index`, `enemy`)을 쓴다.
- 허용은 업계 표준 약어(URL, ID, API, HTTP, JSON, CSS, HTML, DOM, UI)와, 도메인에서 굳은 용어 가운데 문서에 뜻을 적은 것(예: 게임의 `hp`, `fps`)뿐이다. 도메인 용어는 린트 설정의 `no-abbreviations` 옵션 `allow`에 적는다.
- 외부 라이브러리와 표준 API가 정한 이름(`clientX`, `dataset` 등)은 그대로 둔다.
- `no_abbreviations.mjs` ESLint 규칙이 오류로 강제한다. 이름을 낱말로 나눠 두 글자 이하 낱말과 정해진 줄임말 목록을 잡는다. 규칙을 끄거나 줄 단위로 비활성화하지 않는다. 목록에 없는 줄임말은 사람이 읽어 잡는다.
- 새 줄임말이 발견되면 그 줄임말 전체를 목록에 더하고 저장소 전체에서 전수 검색해 고친다.

## 이름 — 그 밖의 기본 규칙

- 함수 이름은 동사로 시작한다(`moveWorker`, `buildFlow`). 값을 돌려주는 함수는 이름에 무엇을 돌려주는지가 드러난다.
- 불리언은 `is`, `has`, `can`, `should`로 시작하고 부정형(`isNotReady`)은 쓰지 않는다.
- 단위가 있는 값은 이름이나 타입에 단위를 드러낸다(`Seconds`, `Pixels`, `Radians`).
- 같은 개념은 같은 낱말로 쓰고 다른 개념에 같은 낱말을 쓰지 않는다.
- 상수는 `UPPER_SNAKE_CASE`이고, 값만 보고 뜻을 알 수 없는 숫자에는 이름을 붙인다.
- CSS와 HTML의 id와 class 이름은 kebab-case로 쓴다(`loading-bar`). camelCase를 쓰지 않는다.


## 기본 코딩 규칙

- `any`와 근거를 적지 않은 `as` 단언을 쓰지 않는다. 타입을 좁혀서 해결한다.
- 빈 `catch`를 쓰지 않는다. 오류는 삼키지 않고 즉시 눈에 띄게 드러낸다.
- `const`가 기본이고 `let`은 값이 바뀌어야 할 때만 쓴다.
- 모듈을 불러오는 것만으로 부작용(이벤트 등록, DOM 접근, 타이머)이 일어나지 않게 한다. 부작용은 이름이 드러나는 함수 안에서 일으킨다.
- 전역 가변 상태는 한 객체에 모으고 그 객체를 고치는 곳을 줄인다.
- 쓰이지 않는 코드, 주석 처리된 코드, 디버그 출력(`console.log`, `debugger`)을 남기지 않는다.
- 같은 모양의 코드는 세 번째에 추출한다.
- 테스트 이름은 동작을 한 문장으로 말한다.

## 파일명과 export 일치 — 절대 규칙

파일명으로 내용을 정확히 예측할 수 있어야 한다.

### 파일 하나는 대표 하나

- `moveWorker.ts`는 `export default function moveWorker`를 낸다.
- `Enemy.ts`는 `export default type Enemy`를 낸다. 타입 하나만 담은 파일도 같다.
- 대표 export는 `export default`로, 파일명과 이름을 맞춘다.
- 보조 export(타입·상수 등)는 named export로 함께 내보낼 수 있다.
- **`import { X } from ".../X"` 형태(파일명과 같은 이름을 named import로 가져오는 것)는 금지한다.** 파일이 대표 하나를 `export default`하면 가져오는 쪽도 `import X from ".../X"`로 default import한다.

### 여러 함수를 묶을 때는 복수형 의미의 파일명을 쓴다

- `utils.ts`, `helpers.ts`처럼 여러 함수를 named export로 내보낸다. 이 경우 `export default`를 억지로 맞추지 않는다.
- **여러 파일에서 공유하는 상수는 `constants.ts`에 `UPPER_SNAKE_CASE` named export로 둔다.** 상수 하나만 담더라도 전용 파일로 default export하지 않는다.
  import는 `import { PRODUCT_NAME } from './constants'` 형태를 쓴다.

## 조건식과 인자 — 읽히는가로 판단한다

- **`if`·`while`의 조건식과 삼항 연산자의 조건은 한 줄에 들어가는 짧은 식이다.** 길어지면 이름 있는 변수나 함수로 추출해 `if (isEligible(order))`처럼 읽히게 쓴다. 조건식을 여러 줄로 나누어 쓰지 않는다.
- 함수 인자는 3개 이하다. 이 숫자는 읽기 쉬운지를 가늠하는 지표이지 기계적으로 맞출 목표가 아니다. 인자를 받는 방식은 호출하는 자리에서 읽히는지로 정한다.
  - 호출하는 자리에서 값의 뜻이 드러나지 않으면 인자가 하나여도 이름 있는 객체(Receive an Object)로 받는다. 불리언 플래그, 같은 타입의 숫자나 문자열이 이웃한 경우가 대표적이다.
  - 좌표나 쿼터니언(x, y, z, w)처럼 순서가 곧 뜻인 값은 넷이어도 그 순서대로 받는다.
  - 그리기 도구나 월드 같은 문맥은 첫 인자로 두고 객체에 넣지 않는다.
- 이름, 설명 주석, 테스트가 있는데도 읽기 어렵다면 이름이나 설명이 부족한 것이다. 함수를 나누면 읽기 어렵다는 이유로 나누기를 미루지 않는다.
- 한 규칙의 입력, 조건, 진행, 결과는 한 폴더에 모은다. 규칙 하나를 바꾸려고 여러 파일을 오가야 하면 응집이 약한 것이다.
- 위 기준을 어긴 곳을 찾는 검색 결과는 후보일 뿐이다. 후보마다 호출하는 자리에서 읽히는지 사람이 읽어 판단하고 「바꿈」 또는 「남김과 이유」로 분류한다.
- 도구가 강제할 수 있는 규칙(중괄호, 미사용 코드, 복잡도)은 린터 설정으로 강제하고, 도구가 잡지 못하는 규칙(조건식 길이, 읽히는 인자, 응집)은 검색 명령으로 후보를 뽑아 사람이 판정한다.
- 이 파일의 규칙이 바뀌면 같은 턴에 프로젝트의 규칙 복사본과 린터 설정을 맞추고, 어긋난 코드를 전수 검색해 고친다.
- **TypeScript는 5.x를 쓴다. 7은 쓰지 않는다.** 안정화되기 전까지 쓰지 않는다.
- **쓰레기 코드는 금지한다.** 쓰이지 않는 코드, 주석 처리된 코드, 디버그 잔재, 중복, 지표만 맞추려는 의미 없는 래퍼를 남기지 않는다. 상세는 `quality-score.md`가 담는다.
- **코드와 설계를 고친 뒤에는 항상 품질 점수를 계산한 다음에 보고한다.** 계산하지 않고 품질을 말하지 않는다.
- 린트 경고도 오류로 취급한다. 린트 스크립트는 `biome check --error-on-warnings .`처럼 경고가 한 건이라도 있으면 실패하게 둔다.
- **한 줄 JSDoc(`/** 설명 */`)은 절대 금지다. 예외가 없다.** 내용이 짧은 한 문장이어도 `/**`, ` * 설명`, ` */` 세 줄로 나눠 쓴다. `no_single_line_jsdoc.mjs` ESLint 규칙이 오류로 강제하며, 이 규칙을 끄거나 줄 단위로 비활성화하지 않는다. 고친 뒤 `grep -rnE '^\s*/\*\*.*\*/\s*$' src e2e`가 0건인지 확인한다.

## 도구와 작업 방식

- TypeScript는 5.x를 쓴다. 7은 쓰지 않는다.
- 패키지 관리자는 pnpm만 쓴다. `package.json`의 `packageManager`와 `engines.node`, 저장소 맨 위의 `.nvmrc`, `pnpm-lock.yaml`을 맞춰 둔다.
- 작업하다 만난 쓰레기 코드와 규칙 위반은 누가 만들었든 같은 작업에서 고친다. 검사에서 나온 경고도 오류로 보고 고친다.
- 고친 뒤에는 `pnpm run check`를 통과시킨다.
